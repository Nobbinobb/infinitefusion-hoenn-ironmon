# PIF2: Ironmon Roadmap

## Project goal

Build an IronMon-style mode for Pokemon Infinite Fusion 2: Hoenn with seeded,
consistent randomization, fusion-aware encounter pools, higher difficulty, and a
fast reset back to the starter selection.

The existing proof of concept in `Data/Scripts/997_Ironmon` has demonstrated
that the following are feasible:

- Adding Ironmon to the game mode selection.
- Applying preset Pokemon, trainer, and item randomization.
- Randomizing scripted and fused encounters.
- Capturing a hidden checkpoint immediately before starter selection.
- Reloading that checkpoint with a new randomization by pressing F7.

## Agreed first-version rules

### Fusion policies

Wild Pokemon and trainer Pokemon have separate fusion-policy settings.

Each can be configured as:

1. **Mixed**
   - 50% chance to select a normal Pokemon.
   - 50% chance to select a fusion with a custom sprite.
2. **Custom Fusions Only**
   - Select only fusions with custom sprites.
3. **Normal Only**
   - Select only non-fused Pokemon.

Autogenerated fusion sprites are excluded from every policy.

The category is selected before the species in Mixed mode. This prevents the
much larger fusion pool from making normal Pokemon effectively disappear.

### Automated pivot loop

- The player has at most one usable party Pokemon.
- Every covered acquisition is resolved immediately without inspecting the new
  Pokemon's summary data.
- A normal current Pokemon and normal candidate can be swapped or consumed in a
  seed-consistent random fusion.
- A newly obtained fusion can be kept, reversed once, or unfused once.
- Player-created fusions and completed caught-fusion pivots cannot later be
  reversed or unfused.
- Unfusion uses the configured Random Component or Player Choice rule.
- Transformations cannot be chained, and every pivot ends with exactly one
  usable Pokemon.

The detailed action table, fusion mapping, data ownership, exclusions, and
acceptance criteria are defined in `PIVOT_SYSTEM.md`.

### Difficulty

- Ironmon automatically enables the game's internal Hard Mode.
- Hard Mode remains enabled for its AI and other behavioral changes.
- Battles are locked to 1v1 for the first version. The Gameplay Options
  `Battle type` control is unavailable while Ironmon is active.
- The Optional Challenge `Level Caps` setting is locked off. This is separate
  from Ironmon's absolute level-100 limit below.
- The Optional Challenge `No reviving` setting is locked on.
- The Optional Challenge `No heals (overworld)` setting is locked on.
- Wild Pokemon levels are 160% of their original levels.
- Trainer Pokemon levels are 160% of their original levels.
- The internal Hard Mode level multiplier must not stack with the Ironmon
  multiplier. The final level is based on `original level * 1.6`.
- Levels are capped at 100.
- Gym Leaders always use six Pokemon.
- Ordinary Gym Trainers are not expanded to six Pokemon.

### Reset behavior

- The game automatically captures a hidden checkpoint immediately before the
  starter selection.
- F7 reloads that checkpoint and generates a new run.
- Resetting preserves the selected Ironmon configuration.
- The player does not repeat character creation or the opening town sequence.

## Milestone 1: Stable configurable foundation

Milestone 1 converts the proof of concept into a maintainable mod foundation.
It is intentionally divided into small steps that can be implemented and tested
independently.

### Step 1.1: Project structure and proof-of-concept extraction

Status: **Complete**

- Create separate source, documentation, and distribution directories.
- Split the single proof-of-concept script into focused Ruby files.
- Keep documentation and all non-Ruby files outside `Data/Scripts`, because the
  game evaluates every file in that directory as Ruby.
- Preserve current proof-of-concept behavior without adding new rules.
- Add a version constant and a minimal compatibility check.

Acceptance criteria:

- The game starts without script errors.
- Ironmon still appears in the mode menu.
- The opening scripted fusion battle is randomized.
- The pre-starter checkpoint is created.
- F7 returns to starter selection with new mappings.

### Step 1.2: Persistent Ironmon configuration model

Status: **Complete**

- Add a configuration object stored in save metadata.
- Store wild and trainer fusion policies separately.
- Define stable policy identifiers rather than relying on menu indexes.
- Preserve configuration when loading the checkpoint.
- Regenerate mappings while retaining configuration on F7 reset.
- Add safe defaults and migration behavior for proof-of-concept saves.

Acceptance criteria:

- Configuration survives saving and loading.
- F7 changes the run seed but not the chosen policies.
- Older Ironmon saves receive documented defaults instead of crashing.

### Step 1.3: Ironmon configuration screen

Status: **Complete**

- Show the screen after selecting Ironmon and before generating mappings.
- Configure the wild Pokemon fusion policy.
- Configure the trainer Pokemon fusion policy.
- Show descriptions for Mixed, Custom Fusions Only, and Normal Only.
- Provide Back and Confirm actions.
- Display a final summary before beginning the run.

Acceptance criteria:

- All nine wild/trainer policy combinations can be selected.
- Back navigation does not partially apply settings.
- Confirmation generates the run exactly once.
- The configuration screen is skipped during F7 resets.

### Step 1.4: Custom-sprite fusion pool service

Status: **Complete**

- Build one validated pool of custom-sprite fusion species.
- Exclude normal species, autogenerated fusions, invalid IDs, and triple/special
  fusion IDs that cannot be used normally.
- Cache the pool for run generation rather than scanning for every encounter.
- Fail with a clear message if the pool cannot be loaded.
- Record enough pool information to reproduce consistent mappings within a run.

Acceptance criteria:

- Every fusion selected by Ironmon has a custom sprite.
- Missing or malformed sprite entries do not crash generation.
- Pool generation does not perform repeated expensive scans during gameplay.

### Step 1.5: Separate wild and trainer species generators

Status: **Complete**

- Replace direct dependence on the built-in shared species mapping where the
  separate policies require different results.
- Generate deterministic wild and trainer mappings from the run seed.
- Implement Mixed as a 50/50 category choice.
- Implement Custom Fusions Only and Normal Only.
- Route ordinary, static, scripted, gift, starter, and trainer-placeholder paths
  through the appropriate mapping.
- Apply the trainer mapping to cloned battle parties for story-owned teams that
  catch, fuse, unfuse, reverse, or evolve between battles.
- Allow required NPC gift/fusion sequences to accept policy-generated fusions
  and flatten them into legal two-base story fusions.

Acceptance criteria:

- Each policy produces only allowed species.
- Wild and trainer policies operate independently.
- The same source species maps consistently within the same category and run.
- The scripted opening battle follows the wild policy.
- Wally, the Hoenn rival, and rematch trainers cannot bypass the trainer policy
  through story-created party changes.
- Custom Fusions Only cannot block Wally's required gift sequence.

### Step 1.6: Difficulty enforcement and 160% level scaling

Status: **Complete**

- Enable internal Hard Mode when Ironmon begins or is loaded.
- Prevent Ironmon from being switched to Easy or Normal.
- Force the default battle format to 1v1 and disable the Gameplay Options
  `Battle type` control. Preserve encounters which explicitly request a double
  or triple battle.
- Force Optional Challenge `Level Caps` off and prevent it from being enabled.
- Force Optional Challenge `No reviving` and `No heals (overworld)` on and
  prevent them from being disabled.
- Scale wild levels from the unmodified original level by 1.6.
- Scale trainer levels from the unmodified original level by 1.6.
- Avoid stacking the game's 1.2 Hard Mode level modifier.
- Cap every scaled level at 100.
- Cover ordinary, overworld, static, scripted, double/triple, rematch, and custom
  trainer battle paths.

Acceptance criteria:

- A base level 10 wild Pokemon becomes level 16.
- A base level 10 trainer Pokemon becomes level 16, not 19 or 20.
- A base level 80 Pokemon is capped at level 100.
- Hard Mode AI behavior remains active.
- The four locked gameplay/challenge settings cannot be changed while Ironmon
  is active and are restored when loading an Ironmon save.

### Step 1.7: Six-Pokemon Gym Leaders

Status: **Complete**

- Create an explicit, versioned method of identifying Gym Leaders.
- Expand Gym Leader parties to six after normal team loading and randomization.
- Do not expand ordinary Gym Trainers.
- Generate added members using the trainer fusion policy.
- Give added members an appropriate leader level and valid moves.
- Persist generated teams across retries.
- Apply the rule to rematches only when their teams contain fewer than six.

Acceptance criteria:

- Every Gym Leader enters battle with six Pokemon.
- Ordinary Gym Trainers retain their normal party sizes.
- Added Pokemon follow the selected trainer fusion policy.
- Losing and retrying does not reroll the leader's team.

### Step 1.8: Milestone integration and regression pass

Status: **Complete**

- Test all nine fusion-policy combinations.
- Test initial generation, save/load, and repeated F7 resets.
- Test the opening scripted fusion encounter.
- Test representative wild, static, gift, trainer, Gym Leader, and rematch paths.
- Add diagnostic logging for seed, policies, pool size, and mapping generation.
- Package a copy-ready Milestone 1 build.

Acceptance criteria:

- No known startup or reset crashes.
- No selected fusion uses an autogenerated sprite.
- Level scaling and Gym Leader party size match the agreed rules.
- A clean installation procedure is documented and repeatable.

## Milestone 2: Automated single-Pokemon pivot system

Milestone 2 enforces the challenge's catch-and-pivot loop in-game. The usable
party is limited to one Pokemon, every covered acquisition is resolved through
one immediate blind decision, and fusion becomes a deterministic gamble rather
than a voluntary post-catch optimization tool. The complete agreed behavior is
specified in `PIVOT_SYSTEM.md`.

### Step 2.1: Pivot configuration and persistent state

Status: **Complete**

- Add the `:random_component` and `:player_choice` unfusion setting.
- Add persistent run state for pending pivots, discovered fusion mappings, and
  stable acquisition identifiers.
- Define origin and transformation-right markers for fused Pokemon.
- Preserve configuration and generated state across save/load and F7 according
  to the documented rules.

Acceptance criteria:

- Old saves migrate to the documented defaults without crashing.
- The unfusion setting survives save/load and remains selected after F7.
- Pending and completed pivot state cannot be confused after loading.
- Fusion origin markers survive every supported Pokemon storage path.

### Step 2.2: One-Pokemon party and acquisition interception

Status: **Complete**

- Enforce at most one usable party Pokemon.
- Intercept permanent wild catches, static Pokemon, gifts, and trades before
  they can create an extra usable or stored Pokemon.
- Exclude Eggs and temporary story Pokemon until their flows are audited.
- Prevent PC withdrawal and other storage behavior from bypassing the rule.
- Make replacement transactional so a failed pivot preserves the current
  Pokemon.

Acceptance criteria:

- Every covered acquisition starts with no more than one current Pokemon.
- No covered path sends a new candidate to ordinary storage before resolution.
- Completing or failing a transaction never duplicates or accidentally loses
  the current Pokemon.
- Excluded acquisition paths remain playable and are recorded for later audit.

### Step 2.3: Blind pivot interface

Status: **Complete**

- Present only the actions legal for the current and newly obtained Pokemon.
- Block summary inspection of stats, moves, ability, and nature until commit.
- Support Take, Swap, Fuse, Swap and Reverse, and Swap and Unfuse as applicable.
- Prevent cancellation after a successful covered acquisition.
- Permanently discard the previous Pokemon and unused results after commit.

Acceptance criteria:

- The action table in `PIVOT_SYSTEM.md` is enforced for every combination.
- The player cannot inspect hidden candidate data before choosing.
- Every successful action ends with exactly one usable party Pokemon.
- No cancelled screen or error can leave a duplicate, missing, or pending
  Pokemon.

### Step 2.4: Deterministic fusion gamble

Status: **Complete**

- Map each unordered pair of normal input species to one validated custom-sprite
  fusion using a dedicated seed namespace.
- Apply orientation by reversing the shared mapped result rather than rolling a
  second result.
- Hide undiscovered results until the first fusion is committed.
- Track discoveries so later uses of the same pair may show their known result.
- Use normal fusion handling for retained instance data unless explicitly
  overridden by the pivot specification.

Acceptance criteria:

- A+B always produces C within one run and B+A produces only reversed C.
- Save/load preserves mappings and discoveries; F7 generates new mappings.
- Results contain only validated normal two-species custom fusions.
- Runtime call order, personal IDs, preview cancellation, and reversal cannot
  reroll an outcome.

### Step 2.5: Caught-fusion reversal and unfusion

Status: **Planned**

- Allow a newly caught fusion one immediate keep, reverse, or unfuse outcome.
- Implement both Player Choice and Random Component unfusion behavior.
- Make random component assignment seed-derived, acquisition-stable, and
  independent of orientation.
- Disable later reversal or unfusion of player-created and processed fusions.
- Disable ordinary fusion and reversal item paths while Ironmon is active.

Acceptance criteria:

- A caught fusion receives at most one transformation during its pivot.
- Random Component cannot be rerolled by save/load or orientation changes.
- Player Choice exposes component identity but no summary information.
- Reverse-then-unfuse, unfuse-then-fuse, and every later transformation chain
  are impossible.

### Step 2.6: Pivot integration and regression pass

Status: **Planned**

- Audit catches, visible encounters, gifts, static Pokemon, trades, storage,
  scripted acquisitions, and mandatory party assumptions.
- Test every current/candidate combination and both unfusion settings.
- Test save/load, F7, failure recovery, and repeated discovered mappings.
- Document deferred Egg, temporary-party, form, and special-fusion behavior.
- Package release `0.2.0` as `Ironmon-v0.2.0-pivot-system.zip`.

Acceptance criteria:

- The full checklist in `PIVOT_SYSTEM.md` passes on a clean installation.
- No covered acquisition or item path bypasses the one-Pokemon invariant.
- No known story progression path is blocked by the party restriction.
- The release build is reproducible and includes its validation record.

## Milestone 3: Pokemon data randomization

Milestone 3 adds the Pokemon data randomizers one at a time. Each completed
step produces a cumulative, installable release build. Minor versions represent
new randomization features; patch versions are reserved for fixes to an existing
release. Version `1.0.0` remains reserved for the complete first public version.

Planned release sequence:

1. Ability randomization: `0.3.0`.
2. Base-stat randomization: `0.4.0`.
3. Level-up move randomization: `0.5.0`.
4. Evolution randomization: `0.6.0`.
5. Fusion inheritance rules: `0.7.0`.
6. Milestone-wide integration and regression: `0.8.0`.

Release builds are cumulative. For example, `0.5.0` contains ability,
base-stat, and level-up move randomization.

### Step 3.1: Ability randomization

Status: **Planned**

- Generate seeded, run-consistent ability assignments.
- Define handling for normal ability slots and hidden abilities.
- Define exclusions or restrictions for disruptive abilities.
- Apply the assignments consistently to normal Pokemon and fusions.
- Add an in-game inspection tool for generated abilities.
- Package release `0.3.0` as `Ironmon-v0.3.0-abilities.zip`.

Acceptance criteria:

- The same species and ability slot resolve consistently throughout one run.
- A new run seed generates new assignments.
- Save/load preserves assignments and F7 generates new assignments.
- Every assigned ability is valid under the agreed restrictions.
- Normal Pokemon and fusions follow the documented inheritance behavior.
- The inspection tool displays enough information to validate assignments.

### Step 3.2: Base-stat randomization

Status: **Planned**

- Define whether base-stat totals are preserved and how values are distributed.
- Establish safe minimum and maximum values.
- Handle unusual species such as Shedinja explicitly.
- Generate seeded, run-consistent base stats.
- Extend the inspection tool to display original and generated stats.
- Package release `0.4.0` as `Ironmon-v0.4.0-base-stats.zip`.

Acceptance criteria:

- Generated stats obey the agreed total and per-stat limits.
- The same species has consistent stats throughout one run.
- Save/load preserves stats and F7 generates new stats.
- Special species remain mechanically valid.
- Fusions follow the documented inheritance behavior.

### Step 3.3: Level-up move randomization

Status: **Planned**

- Define type preference, duplicate handling, and excluded moves.
- Guarantee usable early-game attacking options.
- Cover level-1, level-up, and evolution-learned moves where applicable.
- Generate seeded, run-consistent learnsets.
- Extend the inspection tool to display generated learnsets.
- Package release `0.5.0` as `Ironmon-v0.5.0-level-up-moves.zip`.

Acceptance criteria:

- Generated learnsets contain only valid, permitted moves.
- Early Pokemon cannot be left without a usable damaging move.
- The same species has a consistent learnset throughout one run.
- Save/load preserves learnsets and F7 generates new learnsets.
- Fusions follow the documented inheritance behavior.

### Step 3.4: Evolution randomization

Status: **Planned**

- Define strength, stage, and family constraints for evolution targets.
- Prevent loops, invalid targets, and broken evolution chains.
- Handle level, item, trade, friendship, and special methods.
- Generate seeded, run-consistent evolution mappings.
- Extend the inspection tool to display generated evolution chains.
- Package release `0.6.0` as `Ironmon-v0.6.0-evolutions.zip`.

Acceptance criteria:

- Every generated evolution is reachable and valid.
- Evolution mappings contain no accidental loops.
- The same source species evolves consistently throughout one run.
- Save/load preserves mappings and F7 generates new mappings.
- Fusions evolve according to the documented inheritance behavior.

### Step 3.5: Fusion data inheritance rules

Status: **Planned**

- Finalize how head and body data combine for randomized abilities.
- Finalize how head and body data combine for randomized base stats.
- Finalize how head and body data combine for randomized learnsets.
- Finalize how component evolutions affect fused Pokemon.
- Cover directly encountered and pivot-generated fusions without losing run
  consistency.
- Respect the pivot system's prohibition on later reversal and unfusion.
- Package release `0.7.0` as `Ironmon-v0.7.0-fusion-inheritance.zip`.

Acceptance criteria:

- Every randomized data type has one documented fusion rule.
- Directly encountered and pivot-generated copies of the same fusion expose
  consistent species-owned data.
- Fusing and unfusing cannot create invalid Pokemon data.
- Save/load and F7 follow the same deterministic rules.

### Step 3.6: Milestone integration and regression pass

Status: **Planned**

- Test all Pokemon data randomizers together.
- Test initial generation, save/load, and repeated F7 resets.
- Verify inspection tools for normal Pokemon and fusions.
- Record diagnostics sufficient to reproduce generated data.
- Document compatibility, exclusions, and known exceptions.
- Package release `0.8.0` as `Ironmon-v0.8.0-randomization.zip`.

Acceptance criteria:

- All randomizers are deterministic within a run and change on F7.
- No generated ability, stat set, learnset, or evolution is invalid.
- Normal and fused Pokemon follow the documented rules.
- The complete regression checklist passes on a clean installation.
- Every feature release can be built reproducibly.

## Later milestones

### Milestone 4: Full game-path coverage

- Complete audits of encounters, gifts, static Pokemon, trainers, rematches, and
  special battles.
- Compatibility handling for event paths that bypass standard systems.

### Milestone 5: Remaining challenge rules

- Run failure detection.
- Optional automatic reset after losing.
- Attempt counter and run statistics.

### Milestone 6: Release quality

- Installer or copy-ready package.
- Game-version compatibility detection.
- Save migration and upgrade handling.
- User documentation and changelog.
- Release regression suite.

## Working rule

Only one milestone step should be implemented at a time. Each step must pass its
acceptance criteria before the next step begins. If engine behavior discovered
during implementation changes the design, update this roadmap before continuing.
